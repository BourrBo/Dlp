# P16 security design and open items

## Controls implemented

- Organization identity is taken from the authenticated principal. Connector IDs and request bodies cannot select an organization. Connector and state SQL predicates bind both IDs to the principal organization; PostgreSQL additionally enforces forced RLS.
- Connector rows contain a Vault secret reference and non-secret configuration only. Refresh tokens are written to P09 Vault. Access tokens exist only for a single backend operation. API status models contain no credential field.
- OAuth state is random, short lived, one use, PostgreSQL-persisted, and tenant-RLS protected. Only a SHA-256 digest of state is stored. The row binds organization/principal/provider/connector/member/role/session/redirect and PKCE verifier; an atomic update marks it consumed and permits one callback winner. The provider redirect does not carry the application's Bearer header; the callback instead consumes the one-time state and revalidates the bound user's active membership and session in PostgreSQL before exchanging the code. PKCE uses S256. Callback URI is fixed configuration and must be HTTPS. Token/API targets are fixed Google hosts; user-supplied URLs and redirects are rejected.
- Google HTTP reads are bounded to 2 MB and use a 10-second timeout; redirects are disabled. Retry attempts are limited to four and only retryable 429/5xx/network/quota conditions retry. Error bodies are not returned to callers or logged.
- Connector audit metadata contains operation/provider/count only; access tokens, OAuth codes, refresh tokens, content and headers are excluded. OAuth client ID and client secret are deployment-level bootstrap configuration (`GOOGLE_OAUTH_CLIENT_ID`, `GOOGLE_OAUTH_CLIENT_SECRET`), not tenant-owned provider credentials, so they intentionally remain deployment configuration rather than P09 tenant Vault entries. Operators must provide those values through the deployment secret manager. Tenant-specific refresh tokens use P09 Vault; access tokens are ephemeral.
- Initial inventory enumerates one bounded Drive `files.list` page per sync invocation, persists its opaque page cursor under tenant RLS, and retains the start change token captured before enumeration. Incremental changes begin from that token after inventory finishes; sync never re-runs the full inventory after completion. Each page's scan handoff must succeed before its cursor is persisted.
- Shared-drive flags are used. Shortcut targets are deduplicated. Quarantine fails closed as unsupported until a controlled destination and reversible audit record exist.

## Scope and risk notes

Google Drive scope is the restricted `https://www.googleapis.com/auth/drive` scope because the product objective includes organization-wide change tracking, permission inspection, permission deletion and quarantine moves. `drive.metadata.readonly` cannot write permission changes; `drive.file` limits access to app-opened/shared files and cannot provide a full organization inventory. Restricted-scope verification/assessment is a production prerequisite. Refer to [Google's scope documentation](https://developers.google.com/workspace/drive/api/guides/api-specific-auth).

## Open security gaps and scope limits

- P16 sends normalized metadata (not file contents) through existing `scan()`. Production P1 stages must be configured by the host. No Drive file content download/export or parsing is implemented.
- P05/P07 are invoked through the existing scan pipeline when its configured policy evaluator returns a decision. The owner/admin share-revoke route requires a P05 `REVOKE_SHARE` decision and returns pending approval. The P07 approval endpoint is the only path that invokes the configured connector executor; pending, rejected, foreign-tenant and self-approval requests do not invoke it. P07 receives connector identifiers through a backend-only `ScanRequest` private attribute, never the client-controlled `context`; the executor binds organization identity from the verified principal and reads only that tenant's connected credential reference under RLS. Quarantine remains unsupported (HTTP 501) until a controlled destination, authorization model and restore record exist.
- HTTP OAuth tests cover common valid, invalid, expired, replayed, tampered, cross-principal, PKCE, provider-denial and redirect-tampering cases. The mounted callback also uses real PostgreSQL state for success, replay, expiry, tenant, principal and PKCE cases; its fixture transport validates the fixed token endpoint without contacting Google. The nine-route matrix covers missing/invalid credentials, scope denials, applicable API-key scope/revocation, foreign resources and interactive-user-only actions.
- Synthetic leakage tests cover callback success/error responses, OAuth transaction persistence, Vault retrieval, P07 action metadata/results, approval responses, audit metadata and serialized connector status. They are representative boundary checks and do not instrument every logger, exception surface or database column. The configured pre-commit Gitleaks/hardcoded-secret hook passed. Standalone Gitleaks 8.28.0 history and tracked-worktree scans also passed with exact-string fixture allowlists; its synthetic canary was detected, including from a path containing an allowlisted fixture.
- No configured tenant domain means user/group shares cannot be confidently labeled external. Inherited permissions and restored changes need additional fixtures/semantics.
- P14 deletion cascades connector rows/state and Vault org secrets via their own tenant relationship, but connector-specific lifecycle/export acceptance tests are not written.

## Test distinction

Current P16 provider evidence is deterministic fixture/mock testing plus actual PostgreSQL RLS, migration and persisted OAuth callback testing. It is not live Google OAuth or Drive API validation. No Google API credentials are stored in this repository. The configured pre-commit Gitleaks/hardcoded-secret hook passed; the standalone CLI is unavailable.

An earlier `detect-secrets --no-verify` scan reports 12 keyword heuristics. Eight are `backend/app/auth/roles.py` lines 10–11 (`API_KEYS_READ`, `API_KEYS_WRITE`) and `backend/app/contracts/audit_event.py` lines 14–15 and 36–39 (`API_KEY_CREATED`, `API_KEY_REVOKED`, and `SECRET_*` audit action names); these are permission/action vocabulary. Four are explicit synthetic `TEST_*_DO_NOT_LEAK` markers in `tests/isolation/test_postgres_p16_connectors.py`. Gitleaks 8.28.0 history and tracked-worktree scans passed after reviewing the known synthetic findings and allowing only the exact captured values; no test paths are excluded. A synthetic canary was detected both in an ordinary file and in a path containing an allowlisted fixture. These results do not claim that every runtime log or external provider response was scanned.
